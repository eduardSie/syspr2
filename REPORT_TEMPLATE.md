## 1. Програма й оптимізація

[`dot_product.c`](./dot_product.c) обчислює скалярний добуток двох масивів
`double`. Обидва масиви разом займають 16 MiB, не враховуючи інші дані
процесу. Значення генеруються детерміновано. Вхідні масиви виділяються з
вирівнюванням 64 байти, але зріз зі зсувом на один `double` уже не має такого
вирівнювання; компілятор використовує невирівняні векторні завантаження.

Сусідні повторення обробляють `N` або `N-1` елементів. Змінні аргументи
заважають винесенню незмінного виклику за межі циклу. Збережений результат
друкується як checksum. Алгоритм та аргументи однакові для обох збірок.

| Варіант | Ключі компіляції |
|---|---|
| Базовий | `-O0 -g -fno-omit-frame-pointer` |
| Оптимізований | `-O3 -march=native -ffast-math -g -fno-omit-frame-pointer` |

Це порівняння всього набору ключів, а не ізольований ефект лише `-O3`.
`-ffast-math` дозволяє reassociation редукції; він змінює гарантії
floating-point і не є універсально безпечним для будь-якої програми.
Для цих скінченних вхідних даних checksum:

* `-O0`: `314110495.249049961567`;
* `-O3`: `314110495.249050855637`.

Абсолютна різниця приблизно `8.94e-7`, відносна — `2.85e-15`.
Векторний порядок додавання та fused multiply-add змінюють округлення.
Програма друкує приблизний GFLOP/s, використовуючи `2*N*repetitions`:
це трохи завищує точну кількість операцій, бо кожен другий зріз коротший.

`perf` мультиплексував лічильники й масштабував їхні значення. Частка
активного вимірювання деяких `cpu_atom` подій становила лише 0.46–1.05%;
для `cpu_core` instructions — близько 49%. Тому ці великі числа не можна
вважати точним підрахунком або надійним коефіцієнтом скорочення інструкцій.
`nan` у деяких метриках означає невизначену метрику, не нуль.

Векторизація підтверджена асемблером і узгоджується зі скороченням часу.
Нижчий IPC не заперечує прискорення: одна векторна інструкція виконує більше
роботи. Зростання backend-bound і LLC miss rate узгоджується з більшим
значенням обмежень виконання/доступу до даних після оптимізації, але самої
цієї статистики недостатньо, щоб довести вузьке місце DRAM. Окремого
узагальненого `cache-misses` у збереженому виводі немає.

## 5. Асемблер і AVX/FMA

Джерела:
[`O0.asm`](./measurements/dot_product_O0.asm) та
[`O3.asm`](./measurements/dot_product_O3.asm).

Фрагмент `O0`:

```asm
movsd xmm0,QWORD PTR [rax]
mulsd xmm0,xmm1
movsd xmm1,QWORD PTR [rbp-0x8]
addsd xmm0,xmm1
movsd QWORD PTR [rbp-0x8],xmm0
add   QWORD PTR [rbp-0x10],0x1
```

`mulsd`/`addsd` — скалярні SSE2-операції над одним `double`. Сума та
індекс зберігаються на стеку; кожен елемент потребує багатьох інструкцій.

Фрагмент основного циклу `O3`:

```asm
vmovupd     ymm4,YMMWORD PTR [rax]
vmovupd     ymm5,YMMWORD PTR [rax+0x20]
vmovupd     ymm6,YMMWORD PTR [rax-0x40]
vmovupd     ymm7,YMMWORD PTR [rax-0x20]
vfmadd231pd ymm0,ymm4,YMMWORD PTR [rcx-0x80]
vfmadd231pd ymm2,ymm5,YMMWORD PTR [rcx-0x60]
vfmadd231pd ymm1,ymm6,YMMWORD PTR [rcx-0x40]
vfmadd231pd ymm3,ymm7,YMMWORD PTR [rcx-0x20]
```

Це вибрані рядки; між завантаженнями в оригіналі оновлюються адреси.
`ymm` має 256 біт і вміщує 4 числа `double`. `vmovupd` завантажує їх без
вимоги вирівняної адреси. `vfmadd231pd` виконує packed multiply-add:
`destination = source1 * source2 + destination`, із одним округленням
для кожного fused результату. Чотири такі інструкції та чотири акумулятори
обробляють 16 елементів за ітерацію основного розгорнутого циклу.
Одна 256-бітна FMA виконує 4 множення і 4 додавання, тобто 8 FLOP.

Після циклу `vaddpd` та `vextractf128` зводять часткові суми.
Залишок обробляється коротшими векторними й скалярними інструкціями.
Ці FP-операції використовують AVX та окреме розширення FMA; називати
`vfmadd231pd` просто «інструкцією AVX2» неточно, хоча CPU підтримує AVX2.
Теоретичні 4 lanes не гарантують прискорення у 4 рази: є редукція,
доступ до даних, інші інструкції та обмеження конкретного CPU.

## 6. Енергія CPU package і приблизний внесок програми

Команди виконані з адміністративними правами, без зміни глобального sysctl:

```bash
sudo perf stat -a -e power/energy-pkg/ -- ./build/dot_product_O0 1048576 1200
sudo perf stat -a -e power/energy-pkg/ -- ./build/dot_product_O3 1048576 1200
```

| Показник | `-O0` | `-O3` |
|---|---:|---:|
| CPU package energy, J | 28.00 | 12.25 |
| Час саме RAPL-вимірювання, s | 3.429809829 | 1.405517523 |
| Середня package power `E/T`, W | 8.164 | 8.716 |

Повна package energy зменшилася на **56.25%**, хоча середня package power
зросла приблизно на 6.76%. Робота завершується швидше.
RAPL не включає всі компоненти ноутбука і не ізолює PID: це енергія
package під час запуску, разом із фоновою активністю.

Наявний короткий тест `sudo perf stat -a -e power/energy-pkg/ -- sleep 1`
дав `3.73 J` за `1.001847452 s`. Як дуже грубу базову оцінку:

```text
P_idle ≈ 3.73 / 1.001847452 = 3.723 W
E_incremental ≈ E_package − P_idle × T
O0: 28.00 − 3.723 × 3.429809829 ≈ 15.23 J
O3: 12.25 − 3.723 × 1.405517523 ≈ 7.02 J
```

Це **модельна оцінка додаткової енергії package**, не вимірювання енергії
виключно досліджуваного процесу. Односекундний `sleep` не є надійним idle
baseline, а запис відео також споживає енергію. Для пункту 3.2 необхідно
явно описати атрибуцію та її похибку; точна ізоляція PID цим способом
не досягнута. Для посилення оцінки потрібні довший idle baseline,
повторні запуски й контроль фонової активності.

|---|---:|---:|

Енергія обчислюється як `Σ (t[i+1]−t[i])*(P[i]+P[i+1])/2`.
Числа перевірено повторним обчисленням із CSV. Оцінка енергії зменшилася

запуски з різними часовими вікнами й джерелами вимірювання.

**Обмеження:** опитування кожні приблизно 0.11 s не означає, що батарейний
контролер так само часто оновлює покази. У `O3` усі 14 значень однакові
(`9.778 W`), а в `O0` є лише два рівні (`9.309` і `9.778 W`). Це не
доказ стабільної миттєвої потужності; вимір надто короткий для точного
енергетичного висновку. Скрипт також може включати до приблизно одного
інтервалу очікування після завершення процесу. Наведено приблизну інтегральну
оцінку, не лабораторно точний вимір; для посилення потрібна довша серія
або зовнішній ватметр.

## 8. Висновки й відтворення

1. У цій сесії оптимізований набір ключів дав прискорення **2.43 раза**
   за `/usr/bin/time` та **2.58 раза** в окремому запуску `perf stat`.
2. Асемблер підтвердив AVX/FMA-векторизацію, розгортання циклу та
   регістрові часткові суми. Результати збігаються з відносною похибкою
   приблизно `2.85e-15` на цих вхідних даних.
3. Повний `cpu-clock` FlameGraph залишає `dot_product` головним гарячим
   стеком; оптимізація скорочує роботу, а не змінює структуру алгоритму.
4. Package energy зменшилась на **56.25%**; батарейна оцінка системної
   енергії — на **61.68%**, але з суттєвими обмеженнями точності.
5. Енергію виключно PID не виміряно. Віднімання idle baseline дає лише
   приблизний додатковий внесок навантаження у споживання package.
